# Security boundaries

The local / Waitress SQLite edition uses one private server/database per organisation. Its businesses share owners, backups and administration. The Vercel candidate uses private organisations in a shared durable PostgreSQL database; every public business entrypoint checks organisation ownership and staff scope before accessing records. This is application-enforced tenancy. It is not independently reviewed tenant database row-level security, and clients receive no direct database access. The new Supabase setup uses an unexposed private schema, revokes Data API roles and enables server-only RLS policies; its dedicated runtime role still relies on application checks for organisation isolation.

Both editions use an explicit allowed origin, role checks, optimistic versions, transaction-scoped command receipts and CSRF verification. HTTPS uses Secure/HttpOnly/SameSite cookies. The local development server binds to loopback and should not be exposed directly. The single-server Docker edition runs Waitress behind its configured HTTPS proxy. The Vercel WSGI boundary validates the canonical HTTPS origin and explicitly allowed preview hosts.

Passwords use salted PBKDF2-SHA256 with 600,000 iterations. Older hashes remain readable for local migration. Local sessions are in memory, so the SQLite edition runs one process with threads and requires sign-in after restarts. Hosted sessions store token hashes, expiry, CSRF secrets and password stamps in PostgreSQL and survive worker restarts. Password changes and disabled accounts invalidate access on the next request. Hosted username/IP attempt limits are database-shared fixed windows.

The private hosted pilot uses an administrator-provided setup invitation of at least 32 characters and an explicit registration flag. Invite registration creates a separate organisation, not an owner of every other customer's businesses. Staff usernames are unique within the hosted service; collisions return an unavailable message. Optional Supabase verified-email sign-in creates its own organisation or consumes a saved staff invitation. Roles and scope never come from browser input or Auth user metadata. See the [email-session boundaries](hosting/supabase/README.md). Email sessions are capped at one hour; disabling the linked Business Desk account revokes online access on the next request. Supabase deletion/sign-out alone does not immediately revoke these application sessions. MFA, SSO and self-service linked-email changes are not implemented. Wider onboarding requires a reviewed operator recovery procedure and appropriate authentication acceptance.

Hosted writes use an organisation transaction advisory lock across workers, bounded pool/lock/statement waits and shared command receipts. Missing database configuration fails closed without creating a temporary SQLite store. A lost response does not prove whether a write committed: retry the original command through Sync. The service does not independently transfer funds or claim settlement from a payment label.

Offline copies are opt-in and encrypted with AES-GCM and a PBKDF2-derived device passphrase. Payroll and commission records are excluded. Offline access expires 24 hours after the last refresh. Already-disconnected devices cannot receive immediate revocation; server permissions are rechecked when syncing. One editing tab per account per browser protects vault writes. Uncertain online command IDs survive a tab refresh in session storage; an encrypted vault can retain permitted drafts across browser sessions. Neither is a server backup or independent financial server.

Server-side application data is not encrypted at the field level. Protect the local volume and offsite backups; configure TLS, provider encryption/access controls and independently tested backups for PostgreSQL. Cloud owner exports contain only their organisation's records and attachments, excluding accounts, passwords and sessions; they are not shared database restore files. Recovery through a provider backup is an operator process affecting the database's organisations and needs an isolated drill.

Original files are downloaded as attachments with `nosniff`; uploaded business logos accept bounded PNG/JPEG content, not active SVG uploads. The cloud request/UI limits differ from local use; see the Vercel runbook. Keep secrets, customer records, local databases and backups out of Git. Repository and CI examples are fictional.

This candidate has not received an independent penetration test. Live Vercel infrastructure, recovery, privacy/retention, account recovery, role acceptance, tax/payroll review and actual business pilot acceptance remain release gates. Report vulnerabilities privately to the repository owner without attaching customer records to public issues.
