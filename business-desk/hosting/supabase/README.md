# Supabase database and verified email sign-in

Use this guide for a **new Business Desk project** in your chosen Supabase organisation. Keep production and preview separate. Do not point it at another application's project or use its records to test. The repository has an optional Supabase Auth bridge and a private PostgreSQL schema; it does not provision a project during a build.

## Operator setup

1. Select the intended organisation, project name, region, billing plan and backup/restore requirements. Confirm the provider cost before creating the project. Choose a database region near Vercel `bom1` where available. Record the selected project reference privately.
2. Install Python 3.12 and the pinned `requirements-vercel.txt`. In a private operator environment set `DATABASE_DIRECT_URL` to the intended project's direct or session-pooler connection **with TLS**. Use the provider's actual connection string; URL-encode password punctuation. The direct migration credential stays out of Vercel runtime and Git.
3. Set `DESK_DB_SCHEMA=business_desk`. For a server runtime role, create a dedicated PostgreSQL login without superuser or `BYPASSRLS`, then set `DESK_RUNTIME_ROLE` to its name. Store its password privately. Run `python3 deploy/setup_supabase.py`. The command creates only the selected application schema and its named Business Desk tables; it never edits `auth`, `storage`, `public` or another application's tables.
4. Setup enables RLS on the application tables and revokes schema/table/sequence access from `PUBLIC`, `anon` and `authenticated`. An optional dedicated runtime role receives explicit access and a server-only RLS policy. **Organisation and staff isolation are enforced by the application**, using verified identities and saved permissions. This policy is not per-tenant database RLS. Do not add the private schema to Data API exposed schemas or grant browser roles access. The migration owner can bypass RLS as PostgreSQL's table owner; use the dedicated role for runtime.
5. Use the actual Supabase transaction-pooler connection string on port `6543` for the serverless runtime role, with `sslmode=require` or certificate verification. Set it as `DATABASE_URL`. Start with `DESK_DB_POOL_SIZE=1`; prepared statements are disabled in this adapter. Verify provider-wide connection limits before changing the pool. The project ref normally forms part of the pooler username; follow the dashboard's connection format.
6. Set `SUPABASE_URL=https://PROJECT_REF.supabase.co`, `SUPABASE_PUBLISHABLE_KEY` to that project's publishable key (legacy **anon** key also supported), and `DESK_EMAIL_AUTH=true`. No service-role/secret API key is needed or accepted. These variables are server configuration; provider tokens are never sent to the browser or stored in browser storage.
7. Configure **custom Auth SMTP** and verify the sending domain. Supabase's built-in SMTP is limited to authorised project-team addresses and is unsuitable for customer onboarding. Configure the passwordless/magic-link email template to show `{{ .Token }}` as a numeric sign-in code. Confirm the current project's token length/expiry and rate limits. This app accepts 6–10 numeric digits and imposes additional shared IP/email limits. Enable email sign-in and restrict unwanted Auth methods. Set Auth Site URL to the canonical app origin. Test actual delivery with an explicitly authorised test address; this setup command and CI send no real emails.
8. Add the Vercel variables from [the placeholder template](../vercel/.env.example). Keep `DESK_ALLOW_PREVIEW=false` in production. `DESK_REGISTRATION_ENABLED=true` allows verified emails to create a **new, empty organisation**; `false` permits only existing linked accounts and saved staff invitations. The private `DESK_SETUP_KEY` protects the legacy operator registration path and must remain at least 32 characters. Run `python3 hosting/preflight.py --profile vercel` using this private environment.
9. Import GitHub with Root Directory `business-desk`, build command `python3 deploy/build_vercel.py`, output `public`, Python 3.12, framework Other. The checked-in `vercel.json` is canonical. After an isolated preview passes, deploy the same reviewed source and environment to the canonical domain. Verify health, email signup, two separate organisations, invitation roles, collection retry, analytics, export, print and account disable. Record the deployment ID and commit.
10. Restore a provider backup into an isolated project and verify the data and access with your runtime role. Confirm SMTP delivery, retention, domain, rollback, owner acceptance and country billing/payroll configuration before live records. A successful CI build is not proof of a hosted restore or real email delivery.

## Owner and staff workflow

New owner: choose “Create your business account” → enter name/email → receive numeric code → verify → configure the business and its own name, country, sector, tax, modules and workflow. A signup cannot join an existing organisation by supplying its ID or role.

Staff: owner opens Settings → Account → saves an email, role, business access and (for a technician) employee link → manually shares the app address. Staff choose sign-in with the invited email and verify its code. The saved role is retained; signup input and Supabase `user_metadata` cannot elevate it. Invitations expire in seven days and can be renewed in Settings. Saving an invitation does not email or contact anyone automatically.

Each email identity belongs to one organisation, which can contain multiple businesses. An email already used by another organisation cannot accept a second invitation. Existing username accounts remain available through the username sign-in option; email signup does **not** take over an account merely because its username matches that address. Linking existing accounts or changing a linked email needs a reviewed administrator migration. Export and verify the old organisation first.

## Sessions and recovery

The server verifies each submitted code through Supabase Auth and retrieves the confirmed identity from `/auth/v1/user`. It then issues a random, hashed application session in PostgreSQL, with Secure/HttpOnly/SameSite cookies and CSRF protection. Email sessions are capped at one hour and the provider's returned token lifetime; there is no background provider refresh token. An expired session requires another email code. Role/active-account state is checked on every application request. Disable a team member in Business Desk to revoke access immediately on their next online request.

Deleting or signing out a Supabase Auth user alone does **not** revoke an already-issued Business Desk session immediately. Also disable the linked app account and invalidate its app sessions. Offline access can remain available for the documented 24-hour encrypted-device window; disconnected devices cannot receive immediate revocation. No MFA/SSO or self-service linked-email change is implemented in this candidate.

Provider failures return bounded, redacted errors; missing database configuration fails closed with HTTP 503 and never uses function-local SQLite. The cloud export contains only organisation records and attachments, excluding accounts/passwords/provider credentials. It is not a database recovery file.

## Existing PostgreSQL installations

If you already use this app in `public`, keep `DESK_DB_SCHEMA=public` and use `deploy/migrate_postgres.py` with a reviewed direct URL to add the optional email tables. The new Supabase guide defaults to a fresh private schema. **Changing the schema variable does not move your data.** Review and test an explicit migration before switching an existing installation. Rerun the private schema security command after migrations to apply policies/grants to new named tables.
